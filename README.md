# 官方优选

Cloudflare 官方 IP 段优选工具（Android + Windows/Linux 桌面版）。

从 Cloudflare 官方公布的 IP 子网列表里随机生成候选 IP，逐个测 RTT 与下载带宽，
挑出延迟低、速度快的那一个。

> **第一次用请看 [使用教程.md](使用教程.md)** —— 安装、参数怎么填、
> 结果怎么读、以及为什么会一直提示「这批 IP 都存在 RTT 丢包」。

## 下载

到 [Releases](../../releases) 页下载：

- **Android**：`guanfang-youxuan-v1.20-universal.apk`（通用，体积大）
  或 `guanfang-youxuan-v1.20-arm64-v8a.apk`（2016 年后的手机，省一半空间）
- **Windows**：`guanfang-youxuan-v1.20-windows-amd64.exe`
- **Linux**：`guanfang-youxuan-v1.20-linux-amd64`

APK 只申请 `INTERNET` 一个权限，没有后台服务、没有开机自启、不读通讯录相册。

## 这个工具做什么、不做什么

**做**：从 Cloudflare 官方公布的子网里随机拼候选 IP，测 RTT 和下载带宽，
告诉你哪个 IP 在你当前网络下最快。

**不做**：任何形式的代理、加速、翻墙。它只输出一个 IP 地址，
拿去做什么由你自己决定。

优选结果与网络环境强相关。换 WiFi、换运营商、换城市，甚至只是过几小时，
最快的 IP 都可能变——这是「用时再扫」的工具，不是「扫一次用一年」。

## 数据来源

子网列表和机房位置表来自第三方公开接口 `baipiao.eu.org`，本项目不托管、
不镜像这些数据，也无法保证该接口的可用性。接口挂了就更新不了数据，
这一点在使用前请知悉。

Cloudflare 是 Cloudflare, Inc. 的商标。本项目与 Cloudflare 官方无任何关联，
名字里的「官方」指的是**数据源是 CF 官方公布的 IP 段**，不是「官方出品」。

## 与「反代优选」的区别

两个独立项目，包名与数据源都不同：

| | 官方优选 | 反代优选 |
|---|---|---|
| 数据源 | CF 官方子网列表（`ips-v4/v6.txt`） | 已验证的 `IP:PORT` 列表（`all.txt`） |
| 候选 IP | 从子网随机拼 | 直接用现成条目 |
| 端口筛选 | 有（多选，实测该端口） | 有 |
| 地区筛选 | 有（**测完再筛**，见下） | 有（列表自带标签，先筛后测） |
| 包名 | `com.gf.youxuan` | `com.cf.ip` |
| 使用门槛 | 无 | 密码 |

两个 App 可以同时装在一台手机上。

地区筛选的实现方式在两边**本质不同**。反代优选的节点列表自带国家标签，
可以先筛掉不要的再测；官方 IP 做不到——落地机房取决于运营商线路，
同一个 IP 在电信和联通下可能落到不同国家，事先无从得知。所以官方优选只能
测完之后从 `CF-RAY` 拿到机房三字码、反查国家，再决定要不要这个结果。

结果就是：**地区筛得越窄，耗时增长越明显。** 随机拼的 IP 大部分是死的，
能连通的里面还要再筛地区，命中率是乘法关系。

## 端口与地区（v1.2 新增）

**端口必须选对，否则优选结果没意义。** Cloudflare 边缘节点不只监听 80/443：

- 明文：80、8080、8880、2052、2082、2086、2095
- TLS：443、2053、2083、2087、2096、8443

v1.1 只测 80/443。于是有个很容易踩的坑：优选出的 IP 拿去接一个跑在 2053 的
节点，客户端会报 `io: read/write on closed pipe`。因为工具验证的是「这个 IP
在 443 上是活的 CF 节点」，而你要用的是 2053——握手能过，数据一发就被掐断。

现在端口可以多选，RTT 和测速都打你选的端口。选得越多候选数成倍增长，会明显变慢。

**地区**：常用地区（香港/台湾/日本/韩国/新加坡/美国）点选，其他地区在输入框里
填 cca2 代码（如 `DE,NL`），两者合并去重。不选=不限。

**高级选项里有「节点域名（SNI / Host）」**，默认折叠，但**强烈建议填写**。

填了它，工具才会用你自己的域名去验证，并检查 Cloudflare 能不能回源到你的服务器
（详见下方「回源校验」）。留空只能验证「这是个活着的 CF 节点」，不保证你的节点能用。
填错会导致全部测不通。

结果输出的是 `IP:端口` 完整地址，点一下直接复制，不用自己拼。

## 回源校验（v1.7 新增）

**问题**：软件报可用、拿去接节点却连不上，客户端提示
`io: read/write on closed pipe`。

**原因**：v1.6 及之前只检查响应头里有没有 `CF-RAY`，**不看 HTTP 状态码**。
而 Cloudflare 回源失败时返回的 `521 / 522 / 523` 错误页**同样带 `CF-RAY`**，
于是「CF 到不了你的服务器」这种 IP 被当成可用报了出来 —— 握手能过，数据一发就断。

免费套餐尤其常见：**部分 Cloudflare IP 段对某些运营商回源不通**（实测电信），
付费套餐和 Argo 隧道不受影响。同一个 IP 用测速域名测是 200，用你自己的域名测就是 523。

**现在**：填了节点域名时，按状态码判断能不能回源：

| 状态码 | 判定 | 说明 |
|---|---|---|
| 101 | 通过 | WebSocket 已升级，隧道确实建立起来了 |
| 2xx / 3xx | 通过 | 你的服务器正常响应 |
| 400 / 404 / 405 / 410 | 通过 | 响应来自你的服务器，回源链路是通的 |
| 403 | 排除 | WAF 拦截或 zone 配置问题 |
| 521 / 522 / 523 / 524 / 525 / 526 / 530 | 排除 | Cloudflare 生成的回源错误页，回源断了 |
| 其他 5xx | 排除 | 源站有问题 |

**为什么 404 放行、523 排除**：两者都带 `CF-RAY`，区别在于谁生成了这个响应。
404 来自你的服务器（证明 CF 摸到了源），523 是 CF 自己生成的（证明回源断了）。
WebSocket 节点的根路径本来就返回 404，把它判死会让所有 WS 节点全军覆没。

**限制**：这套判断按 Cloudflare 官方错误码规范实现，但没有在「免费套餐 + 回源不通」
的真实环境端到端验证过。如果 Cloudflare 那边是直接 TCP RST 而不是返回 523，
这层判断抓不到。

## 地区侦察（v1.6 新增）

选了地区时，正式测试前先做一轮廉价探测：每个子网只拼 1 个 IP、只拿机房代码，
不测延迟也不测速。建立「子网 → 国家」索引后，后续所有轮次只在命中的段里优选，
索引跨轮复用。

在此之前，地区筛选是「测完再丢」——每轮换一批子网就从零重新发现哪些段不匹配，
筛窄地区（比如只要香港）时每轮几百个候选可能只有个位数有用。侦察把单个子网的
发现成本压到约 1/8，且结果不再每轮作废。

**探测失败的子网降级为候补，不直接排除。** 从官方子网随机拼出的 IP 大约只有 1/3
能响应（数据源特性），把探不通的当成「地区不符」会误杀大量好子网。只有明确拿到
机房代码、且国家不在所选范围内时才排除整段。命中的段用尽后才会动用候补段，
地区判定在后续阶段仍然生效。

索引只存在内存里、不落盘：落地机房取决于你的运营商线路，换网络或开 VPN 后
整张表立刻失效。

## 优选逻辑（v1.4 重写）

**测速曾经形同虚设。** v1.2 及之前按延迟排序后逐个测速，遇到第一个达标的就返回。
而期望带宽默认 1 Mbps——几乎任何活着的 CF 节点都能过，于是结果实际等于
「延迟最低的那个 IP」，测速只是走了个形式。延迟低不代表带宽高：同城机房延迟 20ms
但可能已被打满，300ms 的远端反而跑得开。现在测完一批再选实测最快的。

**两阶段测速。** 「测完再选」把每轮成本推到 10 × 5 秒 = 50 秒，质量上去了但慢得
没人愿意用。所以先用 1.5 秒粗测全部候选，再只对最快的 3 个做完整测速：
10 × 1.5 + 3 × 5 ≈ 30 秒，比全量快近一半，选出的仍是实测最快的。粗测的绝对值
不准（TCP 窗口还没涨满，系统性偏低），所以只用来排序，绝不用来判定达标。

**每个子网测 2 个 IP。** 之前每个 `/24` 只随机拼 1 个地址。CF 的 `/24` 通常整段
都是活的边缘节点，但随机挑中的那一个恰好不响应（防火墙、未启用、临时故障），整段
就被放弃了。取 2 个把「整段误判为死」的概率降到接近平方级。

**RTT 少做 2/3 的无用功。** 之前对每个目标做 3 次完整的 TCP + TLS 握手 + HTTP
请求，但延迟统计只用了 TCP 握手时间——TLS 和 HTTP 那部分纯属白做。现在只有第 1 次
做完整流程（验 `CF-RAY` 确认是真 CF 节点），后 2 次只做握手计时。

**同机房限额。** 按延迟排出来的 top 10 经常全在同一个 colo——都是离用户最近的那个
机房。一旦那个机房正好拥塞，整轮 10 次测速测的其实是同一条链路，全部白费。现在每个
colo 最多 3 个名额。名额凑不满也不回填：同机房再多测几个 IP 测的还是那条链路，不如
快点进下一轮换新子网。

**地区筛选按子网跳过。** 同一个 `/24` 里的 IP 基本落在同一个 colo。测到某个 IP
的 colo 不匹配时，整段直接标记跳过，不再逐个测完再逐个丢弃。筛地区时这个优化决定
了能不能在可接受时间内出结果。

**覆盖率下限。** `ips-v4.txt` 有 6500+ 个子网，10 轮 × 每批 100 只覆盖约 15%，
剩下 85% 从来没机会被测到——而「最快的 IP」很可能就在里面。现在轮次用尽后若覆盖率
不足 30% 会继续扫描。达标结果仍然立即返回，所以这个下限只在一直没达标时才延长扫描。

**慢 IP 提前放弃。** 一个跑 200 kB/s 的 IP 原本要占满整个 5 秒预算。现在观察 2 秒
后若速度不到目标的 40% 就换下一个。阈值留得宽是为了不误杀慢启动后追上来的 IP。

**抖动参与排序。** 3 次测量之前只取了平均值。低延迟高抖动的 IP 实际体验很差（表现
为卡顿），只看平均值挑不出来。现在按 20ms 分档，同档内优先选抖动小的——5ms 的差别
感知不到，但抖动大的会明显卡顿。

## 指定 IP 段（v1.20 新增）

主界面新增「指定 IP 段」折叠区。留空是原来的行为（扫官方全部 6500+ 个 `/24`），
填了就**只扫你给的段**。

**为什么需要。** 官方列表是 CF 全部对外宣告的段，其中绝大部分和你所在网络的
实际质量无关，而 `104.16` / `104.21` 这些段早被扫烂。有明确目标时（别人分享的
优质段、自己账户对应的段）直接指定，候选池从六千多压到几十个。实测
`104.17.168.0/22` 四秒出结果，同条件扫官方列表要 14 秒。

**写法。** CIDR（`104.16.0.0/13`）、单个 IP、起止范围（`104.16.0.0-104.16.3.255`）、
IPv6 CIDR 都行。一行一条或用逗号/空格分隔均可，`#` 与 `//` 开头按注释忽略。
上限 20000 个 `/24`，超了会截断并提示。

**大段自动切成 `/24`。** 这是能跑起来的前提，不是优化：抽样器按「子网」批次推进、
每个子网出 2 个候选，直接把一个 `/13` 当成一个子网塞进去，整轮只会测 2 个 IP。
IPv6 切成 `/48`。

**指定段时测完全部子网。** 官方列表模式下覆盖率到 30% 就够了（6500 个子网里
最快的那个大概率能撞上），但你给的池子本来就是精挑的，测 30% 就收手等于把
大部分跳过了。

**指定段时不下载官方列表。** 那个 6500 行的文件根本不会被读，首次使用的人没必要
为它干等，数据源挂掉也不该因此扫不了。`url.txt` 和 `locations.json` 仍然要取。

**边打边校验。** 填错（少个斜杠、粘进中文标点、v4/v6 混填）本来只在点了扫描、
等完初始化之后才暴露。现在输入时就调核心层的 `PreviewIPRanges` 显示「已识别
2048 个 IPv4 /24 子网」或者具体哪一条错了。校验逻辑只留核心层一份——两处各写
一份必然出现「界面放过了、扫描才报错」。

**填了 v4 段却扫 v6 会直接提示切换协议**，而不是让你对着「未找到可用 IP」猜。

## 测速源（v1.19 新增）

这是「优选出来很快、实际用起来很慢」的头号原因。

**旧版的测速地址是别人的域名。** v1.18 及之前固定用 `url.txt` 下发的公共镜像
静态 ISO（`cloudflaremirrors.com` 上的 Oracle Linux）。那条链路和你自己的节点
没关系：吃边缘缓存（没命中时回源那段与被测 IP 无关）、上游随时改版 404、
字节数不可控。更关键的是单一域名等于单一运营商 QoS 策略——中国移动国际出口对
不同域名的限速差别很大。

**现在换成按需生成字节流的端点**，并提供 5 档可选：

| 档位 | 地址 |
| --- | --- |
| 自动选择（默认） | 探运营商后决定 |
| Cloudflare | `speed.cloudflare.com/__down?bytes=99999999` |
| CM提供 | `cf.090227.xyz/__down?bytes=99999999` |
| 移动专属 | `speed.okl.abrdns.com` |
| 手动输入 | 你自己的域名，最准 |

自动档探 `cf.090227.xyz/cf.json` 拿 `asn` + `asOrganization`，判定是移动就随机
换用两个移动友好源之一（随机是为了别把社区资源打挂）。探测请求禁用代理，
与地区判定同一套约定——挂着代理探出来的是代理出口的 AS。

**顺便推翻了一个旧结论。** 代码里曾注明「`speed.cloudflare.com/__down` 只服务
直连边缘节点，非直连一律 403」。指定任意 CF IP 实测三个源全部返回 200，
那个结论是当时测法有误。

**速率限制熔断。** 测速端点会返回 429，旧代码把它混进普通状态失败：连续撞限流时
整轮候选白测，还让限制窗口一直续期。现在连续 3 次就停止继续测速，候选之间留
1200ms 间隔，成功一次即清连续计数。

**测速预算改成硬边界。** `Read` 原本在主循环里同步调用，一个「TCP 通、TLS 握手过、
但数据一个字节都不来」的半死连接能把单次 `Read` 挂到 `client.Timeout`（预算 + 3 秒）
——15 秒档最坏 18 秒卡在一个候选上，一轮 10 个就是三分钟。现在读取在独立 goroutine
里跑，主循环用 `select` 等 deadline，到点立刻收工。

**测速请求禁用 gzip。** Go 默认会加 `Accept-Encoding: gzip` 并透明解压，
累计的是解压后的字节数——遇到高度可压缩的内容速度会被放大几十倍。

## 已修的问题

这份代码基于早期版本，修掉了以下问题：

**扫描永不结束。** 原版内外两层 `for{}` 都没有轮次上限，只要达不到期望带宽就
无限重试。用户把带宽填成 900 Mbps 就等于永久扫描，只能靠点取消。现在有
`maxScanRounds = 10` 上限。

**达不到目标就一无所获。** 原版只在达标时返回，没达标的结果全丢——实测 61 Mbps
本来是个可用 IP，但用户什么都拿不到。现在会返回历轮最佳结果并说明差距。

**测速统计漏掉最后一个窗口。** 原版读到 `err` 就直接 break，导致不满 1 秒的
末尾窗口永不结算。如果整个下载在 1 秒内结束，`maxSpeed` 会是 0——明明下载成功
却报速度为零。现在先结算再判错，并用总字节数兜底算平均速度。

**取消后仍在跑。** 并发信号量在满载时会阻塞，用户点了取消还要等已排队的 IP
测完。现在信号量等待可被取消打断。

**取消被显示成「未找到」。** 结果里没有区分字段，界面把两者混为一谈。现在有
`cancelled` 字段。

**IPv6 前缀长度被忽略。** 原版固定保留前 3 段（48 位）随机后 5 段。CF 目前
公布的确实全是 `/48`，所以恰好正确，但上游一旦给出 `/64`，随机就会覆盖掉子网
自身的位，拼出根本不属于 CF 的地址。现在按实际前缀长度计算。

**每轮重复抽样。** 原版每轮重新洗牌取前 100 个子网，轮与轮之间没有记忆，会反复
测同一批。现在一次扫描内洗牌一次、游标推进，跨轮零重复；扫描结束即释放，
不跨扫描保留，所以换网络环境后所有子网重新平等可选。

**测速用的端口和 RTT 不一致。** v1.1 的测速固定连 80/443，而 RTT 测的是
用户指定的端口。RTT 在 2053 上测通、测速却去测 443，测出来的速度对应的
不是用户实际要用的那个端口。现在两处用同一个端口。

**JDK 路径硬编码。** `android/gradle.properties` 里写死了
`org.gradle.java.home=/root/demo/sdk/jdk`，换一台机器直接构建失败。
现在走 `JAVA_HOME`。

**硬编码常量。** 并发数、测速数量上限、带宽上限提取为命名常量。

**取消后更新数据静默失败。** 做桌面版时发现的：取消扫描会把 context 置为
已取消状态，而 `UpdateData` 不重置它，于是下载函数在第一个取消检查处就返回，
旧文件已删、新文件没下，进度却显示「数据更新完成」——用户要到下次扫描才发现
数据没了。现在 `UpdateData` 返回失败原因（原来返回 void，界面只能无条件报成功），
结束时校验文件是否真的到位，没到位就说明缺了哪几个文件。
0 字节文件（下载中断的残留）也算缺失。

**点了开始立刻点取消，取消会丢。** 核心层在任务开始时重建取消上下文，
而任务跑在后台线程里，所以「派发」和「真正开始」之间有一段窗口，
这期间到达的取消会被重建动作抹掉，用户看到的就是取消按钮失灵。
现在多了 `BeginTask()`：界面在派发前同步调一次，把上下文先建好，
任务接手时沿用而不是重建。

**取消提示写死了「扫描」。** 数据更新走同一个取消通道，
取消更新时却提示「用户已取消扫描」，让人以为点错了按钮。改成中性的「正在取消...」，
具体取消了什么由各任务的收尾消息覆盖。

## 界面调整

**取消独立成一个按钮。** 原来扫描和取消共用一个按钮（扫描中变成「停止扫描」），
用户想重新开始时容易误点成取消，而且取消完还得再点一次才开始。现在扫描按钮
在运行时禁用，下方单独出现取消按钮，任务结束后隐藏。数据更新也可以取消了。

**夜间模式补上 danger 色。** 亮色模式的深红 `#D92D20` 放在深灰背景上对比度不足，
取消和删除按钮都看不清，夜间模式单独给了 `#FF6B5E`。

**页面从三页收敛到两页（v1.10）。** 一度拆成「扫描 / 配置 / 历史」三页，
结果参数和扫描按钮分了家 —— 调个带宽要切页、回来再点扫描。现在参数回归首页
排在按钮和结果下面：跑第二轮通常只想再点一次扫描，不该每次先划过一屏参数。

**输出数量可调 1 / 5 / 10（v1.13）。** 优选出的 IP 过一会儿可能就不好用了，
一次多拿几个省得重扫。备选只显示地址 + 速度 + 延迟，机房和用时对「换下一个」
这个决策没帮助。备选不入历史库 —— 历史只存最优那条。

**分段控件改滑动指示块（v1.15）。** IP 协议、输出数量原来是 `RadioGroup`，
它的选中反馈只能是背景 selector 瞬间替换：高亮块"消失在这里、出现在那里"，
中间没有过程，所以无论动效时长怎么调都还是"啪"一下。改成自绘的 `SegmentedBar`，
指示块从旧位置滑到新位置（340ms，略微过冲再回落），位置和宽度都插值（1/5/10
三格宽度不等，只插位置会在宽度突变时闪一下），文字颜色按指示块的实时距离插值 ——
指示块压在两格之间时两边文字都该是中间色。

顺带消掉一类 bug：`RadioGroup` 靠 view id 追踪选中项，动态创建的子项忘了设 id
就会出现两个同时高亮（v1.13 的「输出数量」正是这么坏的）。现在选中项是一个
`int` 下标，没有这个隐患。

**惯性滑到边界改为反弹（v1.15）。** `SpringScrollView` 原来只接手手指拖动，
惯性滑动（fling）撞到边界时直接交给父类，滚动位置走到 0 或 `scrollRangeY`
就硬生生停住 —— 那个"突然顿一下"就是这么来的。现在按 fling 的剩余速度先冲出去
形变、再弹回来。深度上限压在 `maxPull / 3`：惯性撞边的幅度应明显小于手动拉拽，
否则快滑翻页时每次到底都晃一大下。低于 800 px/s 完全不弹 —— 慢慢滑到底本来就
不该有撞击感，弹了反而像手抖。手指按下会立即中断反弹，避免和新的拖动打架。

## 已知限制

**候选 IP 大部分是死的。** 从子网随机拼 IP 必然如此，所以扫描时会看到「这批 IP
都存在 RTT 丢包，换下一批子网继续」。这是数据源决定的，不是 bug。

**地区筛选只能测完再筛，且会显著变慢。** 官方子网列表不含地理位置信息，
落地机房还取决于运营商线路，无法事先预测。筛得越窄命中率越低。v1.4 的
「按子网跳过」能缓解但无法根治。

**机房位置数据可能滞后。** CF 上线新机房时 `locations.json` 里可能还没有对应
条目，此时查不到国家。这种情况选择**放行**——一律拒绝会让用户在数据更新前
完全拿不到结果。所以极少数结果的国家可能显示为空。

**依赖第三方数据接口。** 见上文「数据来源」，接口不可用时无法更新数据。
指定 IP 段（v1.20）可以绕开这个依赖：那时不会读也不会下载官方列表。

**测速源本身也可能被限速。** 内置的三个源都是公共端点，短时间内反复扫描会撞
HTTP 429，届时会提示「触发速率限制」并提前结束测速。想要完全可控的数字就用
「手动输入」填自己域名下的大文件。

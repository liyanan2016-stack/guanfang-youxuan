# 官方优选

Cloudflare 官方 IP 段优选工具（Android + Windows/Linux）。

从 Cloudflare 官方公布的子网列表里随机生成候选 IP，逐个测 RTT 与下载带宽，挑出你当前网络下最快的那一个。

> 第一次用看 [使用教程.md](使用教程.md)｜每版改了什么看 [更新日志.md](更新日志.md)

## 下载

到 [Releases](../../releases) 页下载：

- **Android**：`guanfang-youxuan-v1.21-universal.apk`（通用）或 `-arm64-v8a.apk`（2016 年后的手机，省一半空间）
- **Windows**：`guanfang-youxuan-v1.21-windows-amd64.exe`
- **Linux**：`guanfang-youxuan-v1.21-linux-amd64`

APK 只申请 `INTERNET` 一个权限，没有后台服务、没有开机自启。

## 做什么、不做什么

**做**：测 RTT 和下载带宽，告诉你哪个 CF IP 在你当前网络下最快。

**不做**：任何形式的代理或加速。它只输出一个 IP 地址。

优选结果与网络环境强相关，换 WiFi、换运营商、过几小时都可能变——这是「用时再扫」的工具。

名字里的「官方」指**数据源是 CF 官方公布的 IP 段**，不是「官方出品」。子网列表与机房位置表来自第三方公开接口 `baipiao.eu.org`，本项目不托管这些数据，接口挂了就更新不了。Cloudflare 是 Cloudflare, Inc. 的商标，本项目与其无任何关联。

## 与「反代优选」的区别

两个独立项目，可同时安装。

| | 官方优选 | 反代优选 |
|---|---|---|
| 数据源 | CF 官方子网列表 | 已验证的 `IP:PORT` 列表 |
| 候选 IP | 从子网随机拼 | 直接用现成条目 |
| 地区筛选 | **测完再筛** | 列表自带标签，先筛后测 |
| 包名 | `com.gf.youxuan` | `com.cf.ip` |
| 使用门槛 | 无 | 密码 |

地区筛选的差别是本质的：官方 IP 的落地机房取决于运营商线路，同一个 IP 在电信和联通下可能落到不同国家，事先无从得知，只能测完之后从 `CF-RAY` 反查。所以**地区筛得越窄，耗时增长越明显**——随机拼的 IP 大部分是死的，能连通的里面再筛地区，命中率是乘法关系。

## 构建

```bash
./build-apk.sh                     # Android debug
./build-apk.sh release             # Android release，需签名配置
./build-desktop.sh                 # 桌面版，交叉编译，不需要 Windows 机器
./build-desktop.sh windows-amd64   # 单个目标
```

工具链目录自动探测（`/tmp/cfip`、`/root/demo`），也可以用 `GF_SDK_ROOT=/opt/toolchain` 指定。两个脚本出包前都会跑 `gofmt` / `go vet` / `go test`，任一失败即中止。

release 签名配置写在 `android/store.properties`（不要提交到 Git）：

```properties
storeFile=guanfang-release.jks
storePassword=***
keyAlias=guanfang
keyPassword=***
```

**签名密钥必须单独备份。** 丢了之后用户没法覆盖安装新版，只能卸载重装（历史记录全丢），而且无法补救——Android 签名密钥不能重新生成。

桌面版 exe 没有代码签名证书，Windows SmartScreen 首次运行会拦一下。

## 设计要点

下面几条是这个工具与「照着官方列表随便测测」的区别所在，也解释了几个反直觉的行为。完整的版本沿革在 [更新日志.md](更新日志.md)。

### 端口必须选对

CF 边缘节点不只监听 80/443——明文还有 8080、8880、2052、2082、2086、2095，TLS 还有 2053、2083、2087、2096、8443。

v1.1 只测 80/443，于是有个很容易踩的坑：优选出的 IP 拿去接一个跑在 2053 的节点，客户端报 `io: read/write on closed pipe`。因为工具验证的是「这个 IP 在 443 上是活的 CF 节点」，而你要用的是 2053——握手能过，数据一发就被掐断。

现在 RTT 和测速都打你选的端口。选得越多候选数成倍增长，会明显变慢。

### 验证必须与真实使用同源

「验证通过」只在探测请求与真实使用请求指向同一目标时才有意义。这条原则在这个项目里踩了三次：

- **只判 `CF-RAY` 存在等于把「摸到了门」当成「门后的隧道通」。** CF 回源失败的 521–526 同样带这个头，于是「CF 到不了你的服务器」的 IP 被当成可用报出来，用户侧表现为连上就断。免费套餐尤其常见：部分 CF IP 段对某些运营商回源不通（实测电信）。现在按状态码白名单判定——放行 101 / 2xx / 3xx / 400 / 404 / 405 / 410，判死 403 / 521–526 / 530 / 其他 5xx。

  分界线是「这个响应由谁生成」：404 来自你的服务器，证明回源通（WebSocket 节点的根路径本来就返回 404，判死它会让所有 WS 节点全军覆没）；523 是 CF 自己生成的，证明回源断。用白名单而不是黑名单，是因为上游未来新增错误码时白名单最坏只是少给一个候选。

- **RTT 与测速用了不同域名。** `testRTT` 拿 `cloudflare.com` 做 SNI+Host，测速却走另一个域名——实测有 IP 对前者返 301 通过、对后者返 403 实际不可用。现在两处对齐，填了自定义域名时以它为准。

- **测速地址是别人的域名。** 见下。

所以**强烈建议填「高级选项 → 节点域名」**：填了工具才会用你自己的域名验证并检查能否回源，留空只能验证「这是个活着的 CF 节点」。填错会导致全部测不通。

### 「最优」的定义容易被实现细节悄悄改写

- **测速曾经形同虚设。** v1.2 及之前按延迟排序后逐个测速、遇第一个达标就返回，而期望带宽默认 1 Mbps——几乎任何活着的 CF 节点都能过，结果实际等于「延迟最低的那个 IP」。延迟低不代表带宽高：同城机房延迟 20ms 但可能已被打满，300ms 的远端反而跑得开。现在测完一批再选实测最快的，只在远超目标（3 倍）时才短路。
- **峰值不是速度。** 原来用 `maxSpeed`，那是 TCP 慢启动后的突发峰值。改成 EWMA 平均。
- **不查状态码等于把错误页当下载内容。** 现在只接受 200/206。
- **单次 TCP 失败就判死太苛刻。** 改成探测 4 次算丢包率，超 50% 判死；排序时丢包率优先于延迟，再看抖动（按 20ms 分档，同档内优先抖动小的——5ms 感知不到，抖动大的会明显卡顿）。
- **测速请求禁用 gzip。** Go 默认加 `Accept-Encoding: gzip` 并透明解压，累计的是解压后字节数，遇到可压缩内容速度会被放大几十倍。

### 为了在可接受时间内出结果

- **两阶段测速。** 「测完再选」把每轮成本推到 10 × 5 秒。所以先用 1.5 秒粗测全部候选，再只对最快的 3 个做完整测速：约 30 秒，比全量快近一半。粗测绝对值不准（TCP 窗口没涨满），只用来排序，绝不用来判定达标。
- **每个子网测 2 个 IP。** CF 的 `/24` 通常整段都是活的边缘节点，但随机挑中的那一个恰好不响应（防火墙、未启用、临时故障）整段就被放弃了。取 2 个把「整段误判为死」的概率降到接近平方级。
- **RTT 少做 2/3 无用功。** 之前每个目标做 3 次完整 TCP + TLS + HTTP，但延迟统计只用 TCP 握手时间。现在只有第 1 次做完整流程（验 `CF-RAY`），后 2 次只做握手计时。
- **同机房限额 3 个。** 按延迟排出的 top 10 经常全在同一个 colo，那个机房一拥塞整轮测的是同一条链路。名额凑不满也不回填——不如快点换新子网。
- **地区筛选按子网跳过 + 侦察。** 同一个 `/24` 里的 IP 基本落在同一个 colo，某个 IP 的 colo 不匹配就整段跳过。选了地区时正式测试前先做一轮廉价探测（每子网 1 个 IP、只拿机房代码），把单个子网的发现成本压到约 1/8，索引跨轮复用、只存内存不落盘（换网络或开 VPN 后整张表立刻失效）。

  **探测失败的子网降级为候补，不直接排除。** 随机拼的 IP 只有约 1/3 能响应，把探不通的当「地区不符」会误杀大量好子网。只有明确拿到机房代码、且国家不在范围内才排除整段。
- **慢 IP 提前放弃。** 观察 2 秒后速度不到目标 40% 就换下一个。阈值留宽是为了不误杀慢启动后追上来的 IP。
- **覆盖率下限 30%。** 6500+ 个子网、10 轮 × 每批 100 只覆盖约 15%，而最快的 IP 很可能就在剩下 85% 里。轮次用尽后若覆盖率不足会继续扫描；达标结果仍立即返回，所以这个下限只在一直没达标时才延长扫描。
- **测速预算是硬边界。** `Read` 原本同步调用，一个「TCP 通、TLS 过、但一个字节都不来」的半死连接能把单次 `Read` 挂到 `client.Timeout`——15 秒档最坏 18 秒卡在一个候选上。现在读取在独立 goroutine 里跑，主循环 `select` 等 deadline。

### 抽样不能有放回

原版每轮重新洗牌取前 100 个子网，轮与轮之间没有记忆，会反复测同一批。现在一次扫描内洗牌一次、游标推进，跨轮零重复；扫描结束即释放，不跨扫描保留——所以换网络环境后所有子网重新平等可选。

### 测速源决定了速度数字有多少参考价值

v1.18 及之前固定用公共镜像的静态 ISO。那条链路和你自己的节点没关系：吃边缘缓存、上游随时改版 404、字节数不可控。更关键的是单一域名等于单一运营商 QoS 策略——中国移动国际出口对不同域名的限速差别很大，这是「优选出来很快、实际用起来很慢」的头号原因。

现在换成按需生成字节流的端点，5 档可选（Cloudflare / CM提供 / 移动专属 / 手动输入 / 自动）。自动档探 `cf.json` 拿 `asn` + `asOrganization`，判定是移动就随机换用移动友好源（随机是为了别把社区资源打挂）；探测请求禁用代理——挂着代理探出来的是代理出口的 AS。

想要完全可控的数字就用「手动输入」填自己域名下的大文件，测的是「CF 边缘 → 回源到你的服务器」这条你真正会用的链路。

**速率限制熔断**：公共端点会返回 429，旧代码把它混进普通失败——连续撞限流时整轮候选白测还让限制窗口一直续期。现在连续 3 次就停止测速，候选之间留 1200ms 间隔。

### 指定 IP 段（v1.20）

官方列表是 CF 全部对外宣告的段，绝大部分和你所在网络的实际质量无关，而 `104.16` / `104.21` 这些段早被扫烂。有明确目标时直接指定，候选池从六千多压到几十个——实测 `104.17.168.0/22` 四秒出结果，同条件扫官方列表要 14 秒。

**大段自动切成 `/24`**（IPv6 切 `/48`）是能跑起来的前提而非优化：抽样器按「子网」批次推进、每个子网出 2 个候选，直接把一个 `/13` 当成一个子网塞进去，整轮只会测 2 个 IP。

指定段时**测完全部子网**（官方列表模式 30% 覆盖率就够，但你给的池子本来就是精挑的），且**不读也不下载官方列表**（首次使用的人不必为那个 6500 行文件干等，数据源挂掉也不该因此扫不了）。

**边打边校验**：调核心层的 `PreviewIPRanges` 实时显示识别结果或哪一条错了。校验逻辑只留核心层一份——两处各写一份必然出现「界面放过了、扫描才报错」。

### 界面

- **两页而不是三页。** 一度拆成「扫描 / 配置 / 历史」，结果参数和扫描按钮分了家——调个带宽要切页、回来再点扫描。现在参数回归首页排在按钮和结果下面：跑第二轮通常只想再点一次扫描。
- **折叠必须留摘要。** 端口、地区、高级选项展开要占掉大半屏，但默认值以外的设置必须能一眼看见，所以收起时标题右侧显示「443 · 香港/日本」这样的摘要。
- **取消独立成一个按钮。** 原来扫描和取消共用一个（扫描中变成「停止扫描」），想重新开始时容易误点，而且取消完还得再点一次。
- **分段控件不用 `RadioGroup`。** 它的选中反馈只能是背景 selector 瞬间替换，动效时长怎么调都是「啪」一下；而且靠 view id 追踪选中项，动态创建的子项忘了设 id 就会两个同时高亮。改成自绘的 `SegmentedBar`，选中项是一个 `int` 下标。
- **滑到边界会回弹。** 不是 bug。没有这个反馈的话滚到边界就是硬生生一停，看着像卡住。惯性撞边的幅度压在手动拉拽的 1/3，低于 800 px/s 完全不弹。

## 已知限制

- **候选 IP 大部分是死的**，所以扫描时会反复看到「这批 IP 都存在 RTT 丢包」。数据源决定的，不是 bug。
- **地区筛选只能测完再筛，且会显著变慢。** 见上文。
- **机房位置数据可能滞后。** CF 上线新机房时 `locations.json` 里可能还没有对应条目。这种情况选择**放行**——一律拒绝会让用户在数据更新前完全拿不到结果，所以极少数结果的国家可能显示为空。
- **依赖第三方数据接口。** 指定 IP 段（v1.20）可以绕开这个依赖。
- **测速源本身也可能被限速。** 内置的三个源都是公共端点，短时间内反复扫描会撞 429。想要完全可控的数字就用「手动输入」。
- **回源校验未在真实的「免费套餐 + 回源不通」环境端到端验证过。** 按 CF 官方错误码规范实现；如果 CF 那边是直接 TCP RST 而不是返回 523，这层判断抓不到。
